The five running examples

Five systems — E1 to E5 — that the course evaluates over and over, introduced in Lesson 3, The Dimensions of Experiment Design. They form a complexity ramp: from a deterministic two-input function, where evaluation looks like unit testing, to systems where even “correct” is a judgment call. The lesson walks E2 and E4 through the design dimensions in depth.

E1Host health anomaly score in monitoring

Compute a single anomaly-severity score for a host from its CPU and memory deviations — the Euclidean distance from “no deviation at all”, then threshold it to fire an alert.

The degenerate case: a pure deterministic function. Exact outputs and near-zero run-to-run uncertainty once the specification and inputs are fixed — evaluation looks like unit testing. (The specification, the alert threshold, and input coverage can still be uncertain.)

def deviation_score(cpu_dev: float, mem_dev: float) -> float:

    if not 0.0 <= cpu_dev <= 1.0:
        raise ValueError(f"cpu_dev must be in [0, 1], got {cpu_dev}")

    if not 0.0 <= mem_dev <= 1.0:
        raise ValueError(f"mem_dev must be in [0, 1], got {mem_dev}")

    return (cpu_dev**2 + mem_dev**2) ** 0.5
deviation_score(0.0, 0.0) == 0.0          # perfectly normal
deviation_score(0.6, 0.8) == 1.0          # clean 3-4-5
deviation_score(1.0, 1.0) == math.sqrt(2) # both metrics maxed out

E2ML classifier for routing tickets to groups

A classification task: classify a support ticket into ONE of five classes — account, order, refund, payment, delivery.

A trained model. The function is learned from data, so uncertainty now lives in the data (sampling, labels), the training run, and the measured score — no longer in the code alone.

E3GenAI few-shot classifier for routing tickets to groups

The same classification task as E2 — five classes, same dataset — but solved by prompting an LLM with a few examples per class instead of training a model.

Three tunable parts — the prompt, the few-shot examples, and the model — so the boundary of the system under eval becomes a choice: are you evaluating the prompt, the examples, the model, or all three together?

E4Self-solve via clustering

Answer support requests without a human: cluster historical requests (which come with their solutions), attach a solution to each cluster, then answer a new ticket by matching it to a cluster and extracting that cluster’s solution.

A multi-stage pipeline with both training-time and inference-time components — and no clean ground truth for “the right solution”.

You could evaluate the clustering, the cluster matching, the solution extraction — or the pipeline end-to-end. Each is a different experiment, with a different data point and a different notion of “correct”. Deciding this boundary is one of the lesson’s central ideas.
